## 第1章 インターネットとネットワークの仕組み

### Q1. インターネットとは
- インターネットと、Webブラウザで見るホームページは違うもの
- インターネットは目に見えない土台・基礎。ホームページは、人間の目に見える情報を検索したり見たりできるもの

### Q2. IPアドレスとポート番号
- localhostとは何を指すか  
  自分のPCを指す
- ポート番号がなぜ必要か  
  フロントエンドとバックエンドのように、同じPC上で同時に動いている複数のプログラムを区別するための番号だから

### Q3. DNS
- DNSはドメインネームシステムの略
- ドメイン名とIPアドレスを紐づけるサービス。IPアドレスはPCにとってわかりやすい住所、ドメイン名は人間にとってわかりやすい住所で、この2つを紐づける役割を持つ
- アドレスバーにアドレスを入力すると、まず該当のIPアドレスを探しに行き、そのIPアドレス宛てに「このページを表示してほしい」と頼みに行っている

### Q4. HTTPとは
- HTTPはHyper Text Transfer Protocolの略
- プロトコルとは「約束事」という意味
- HTTPは、通信を転送するための約束事

### Q5. HTTPとHTTPSの違い
- HTTPは通信が保護されておらず、HTTPSは通信が保護されている
- HTTPのままだと、通信のやりとりの内容を悪意のある人に見られてしまうリスクがあるため、現在はほぼすべてのサイトがHTTPSを使用している

### Q6. リクエストとレスポンス
- レストランに例えると、お客さんが料理を注文するのがリクエスト、それに対して返ってくる料理がレスポンス

### Q7. HTTPメソッド
ネット通販で荷物を送る場面に例えると、以下のように対応する。
- 新しく注文する → POST
- 注文した中身を全部作り直してもらう → PUT
- 注文の一部を訂正してもらう → PATCH
- 注文を取り消す → DELETE
- 注文状況を確認する → GET

### Q8. HTTPステータスコード
- 200 → リクエストが通ってうまく処理された
- 201 → 新しいデータを追加するためのリクエストが成功した
- 400 → リクエストの内容が壊れていて、サーバー側で理解できない
- 404 → URLを間違えているか、削除されているかで、リクエストされたページが見つからない
- 500 → サーバー側でエラーが発生し、リクエストの処理が失敗した

### Q9. JSONとは
- JSONとは、ファイルの書き方のルールのこと
- データが軽く、人間が読みやすく、どの言語でもそのまま使えるため広く使われている

### Q10. APIとは
- APIとは、プログラム同士を繋ぐ役割をするもの
- 直接データベースにアクセスしない理由は、セキュリティが弱くなることと、データベースを変更したときにアプリが壊れやすくなることを避けるため

### Q11. CORSとは
- フロントエンドとバックエンドのように違うオリジン（http/httpsとドメイン名を組み合わせたURL）に、安全にアクセスできるようにするための仕組み

### Q12. クライアントとサーバー
- クライアントは、データなどを要求する役割のもの
- サーバーは、要求されたものに対して結果を返す役割のもの
- このアプリでは、クライアントがブラウザ、サーバーはデータベース、バックエンドはデータベースにとってのクライアントであり、ブラウザにとってのサーバーという二重の役割を持つ

## 第2章 Webアプリケーションの構造

### Q13. フロントエンドとバックエンド
- フロントエンドは人間に見られる画面描画担当、バックエンドは内部の処理担当（前衛と後衛のようなイメージ）

### Q14. 3層構造
- すべてを1つのプログラムに書くと、どこに何が書いてあるのか乱雑になって分かりづらくなる
- 役割を分けることで「これはこの役割を持つもの」というのがシンプルで分かりやすくなるため、3層に分けている

### Q15. データの流れ
「新しいタスクを作成」ボタンを押してからの流れ
1. フロントエンド側で入力された内容を集めて、JSON形式に変換する
2. POSTメソッドを使い、フロントエンドからバックエンドにデータを渡す
3. バックエンドがデータベースにCREATE処理の指示を出し、データベースに保存される
4. データベースへの保存が終わったら、バックエンドはフロントエンドに処理結果を返す
5. フロントエンドが結果を受け取ったら、新しいタスクが「追加」ボタンを押したリストに作られる

### Q16. エンドポイントとURL設計
- `/api/tasks`はタスク全体（集合）、`/api/tasks/{id}`は特定のタスク1つを指す
- `{id}`は、絶対に被らない番号で、タスク1枚1枚を管理するための番号

### Q17. 同期処理と非同期処理
- 同期処理は前の処理が終わってから次に進む処理、非同期処理は前の作業の完了を待たずに次の処理をどんどん行う処理
- 料理に例えると、1品ずつ作るのが同期処理、複数品を同時進行で作るのが非同期処理
- Web通信で非同期処理が必要な理由は、待ち時間が発生すると作業として非効率だから

### Q18. SPA（シングルページアプリケーション）
- 従来のWebサイトはリンクを押すたびに画面が真っ白になって再読み込みされるが、SPAはそれがない
- やり取りするデータの量が少なくて動作が軽く、画面が切り替わる速さも従来のホームページより速いため、ユーザーの満足度も高くなる

### Q19. 入力チェック（バリデーション）の多重防御
- フロントエンドを通さず、バックエンドに直接データを送りつけることが技術的には可能なため、フロントエンド・バックエンド両方で入力チェックが必要

### Q20. エラーハンドリング
- API呼び出しが失敗した場合、何かしらエラーが起きたことを画面に表示するべき
- 何も表示されないと、ユーザーはどうしていいか分からなくなるため

## 第3章 データベースの基礎

### Q21. データベースとは
- データベースとは、大量のデータを保存しておける場所
- ExcelやCSVと比べて優れている点は、複数人が同時に書き込んでも、誰かの変更が勝手に上書きされないこと

### Q22. テーブル・行・列
- テーブル → タスクのリスト全体
- 行（レコード） → タスク1つ分のデータ
- 列（カラム） → 項目名（id、titleなど）

### Q23. 主キー（PRIMARY KEY）
- 主キーとは、他と被らない管理番号
- 必要な理由は、同じタスク名が複数あった場合に、削除や変更をしたいときにどちらに手を加えればいいか分からなくなってしまうから

### Q24. CRUD操作
- CRUDとはCreate・Read・Update・Deleteの略で、データを最低限操作するための機能
- Create → タスクを新規作成
- Read → 該当タスクの検索
- Update → タスクの更新
- Delete → タスクの削除

### Q25. データの制約
- `NOT NULL` → 空白を許さない制約。タイトルを空欄のままでは新規作成や更新ができなくなる
- `DEFAULT 'medium'` → タスクで優先度を何も選ばなかったときに、自動で初期値（medium＝中）が入るようにしておける

### Q26. インデックス
- インデックスとは、本の索引のようなもの。目的の場所だけを読めるようにするもの

### Q27. トランザクション
- トランザクションとは、何か処理を行って、成功するか、失敗したら全部なかったことにする仕組みのこと
- タスクを別カラムへドラッグ移動する操作でこれが重要な理由は、移動時に裏側で複数のデータ（タスク自身の情報や周りの並び順など）が変更される可能性があり、その一部だけが失敗すると、タスクの数は変わらないのに表示上消えたように見えるなど、データがおかしくなってしまうことがあるため（実際に経験したことがある）

### Q28. SQLとORM
- SQLとは、データベースとやりとりするための言語
- ORMの役割は、SQLを直接書かずにデータベースとやりとりできるようにすること

## 第4章 開発プロセスとチーム開発

### Q29. バージョン管理（Git）
- Gitなどのバージョン管理システムとは、ファイルの変更履歴を記録・保存し、複数人での開発を可能にするシステム
- 必要な理由は、複数人で共同開発する際、みんなが1つのメインファイルを書き換えるとコードがぐちゃぐちゃになって分かりにくくなるため、分担して作業できるようにするため
- 使わないと、気づかないうちに他人の変更を上書きしてしまったり、間違った変更をしても前の正常な状態に戻れなくなったりする問題が起きる

### Q30. ブランチとPull Request
- ブランチとは分かれ道のようなもの。機能を実装したいときに、メインの環境とは別の環境で作業できる
- Pull Requestの目的は、レビューをするため
- 全員がmainに直接変更しない理由は、mainに直接変更を加えると、知らない間に上書きされて、さっきまで正常に動いていたものが知らない挙動をし始める可能性があるから

### Q31. コミットメッセージの重要性
- 良いコミットメッセージを書くことが重要なのは、誰が見ても何をしたか分かりやすくするため

### Q32. なぜ技術的な仕組みを理解すべきか
- コードが分からなくてもアプリを動かせるようにはなったが、トラブルが起きたときの対処をAIに全部頼んだとしても、自分に知識があれば原因が分かり、次回に活かすことができるから
